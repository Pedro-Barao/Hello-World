Fundamentação Histórica • 1970 vs 1990

🏛️ 1. O Abismo entre Dois Mundos (O Impedance Mismatch)

No início da computação corporativa, Edgar F. Codd (IBM, 1970) formalizou o Modelo Relacional. O banco de dados pensa exclusivamente em tabelas bidimensionais, tuplas de dados primitivos escalares e integridade relacional via chaves primárias (PK).

Já a Orientação a Objetos de Alan Kay pensa em entidades vivas na memória RAM: encapsulamento, comportamentos (métodos), herança polimórfica e ponteiros de referência (identidade de Heap via obj1 == obj2). Ted Neward denominou essa barreira de "O Vietnã da Computação".

🎭 Metáfora Lúdica do Tradutor Juramentado:
A classe de negócio em Java é um diplomata que só fala português culto (regras de validação). O banco de dados é um diplomata que só fala dialeto SQL antigo. O Padrão DAO é o tradutor juramentado no meio da mesa: ele recebe comandos do Java e gera SQL seguro; quando o banco entrega uma pasta com fichas soltas (ResultSet), o DAO hidrata e monta o objeto Java na memória.

Catálogo Core J2EE • Sun Microsystems (2001)

🚫 2. O Pecado Original: Misturar Regra de Negócio com SQL

Em 2001, a Sun Microsystems publicou o catálogo Core J2EE Patterns. O erro mais amador de um programador é colocar comandos JDBC (Connection, PreparedStatement) dentro das entidades de domínio ou nos botões de telas Swing.

Se você coloca um INSERT dentro de Produto.java, a classe ganha duas razões para mudar (violando o SRP - Single Responsibility Principle): muda se as regras financeiras mudarem e muda se a empresa trocar o SQLite pelo PostgreSQL!

🎮 Metáfora do Controle Remoto Universal (Interfaces):
A Interface DAO funciona exatamente como o controle remoto da sua sala: tem botões bem definidos como salvar(Cliente) e buscarPorId(Long). O seu Controller aperta esses botões sem precisar saber se a TV é Samsung, LG ou Philips (SQLite, PostgreSQL ou Mock em memória).

📐 Arquitetura & Especificação Detalhada do Projeto

PADRÃO ENTERPRISE

Implemente o projeto modular seguindo rigorosamente a separação de responsabilidades (Clean Architecture / MVC):

1. Pacote e Modelo: br.com.bookstore.model.Livro

  • Atributos Privados: Long id, String titulo, String autor, double preco.
  • Dois Construtores:
    • Construtor Completo: (Long id, String titulo, String autor, double preco) — usado para hidratar tuplas do banco.
    • Construtor de Negócio: (String titulo, String autor, double preco) — atribui null ao id.
  • Blindagem de Invariantes de Domínio: O construtor DEVE validar e disparar IllegalArgumentException caso:
    • titulo seja nulo ou vazio (comprimento < 2 caracteres após trim()).
    • autor seja nulo ou vazio.
    • preco seja menor ou igual a 0.0 ("O preço de venda deve ser estritamente positivo").
  • Métodos: Getters completos, setId(Long id) (único setter permitido para sincronizar PK gerada) e toString() formatado.

2. Contrato da Interface: br.com.bookstore.dao.LivroDAO

A camada de negócio não pode conhecer JDBC. Declare o contrato desacoplado:

public interface LivroDAO {
    void salvar(Livro livro);
    Optional<Livro> buscarPorId(Long id);
    List<Livro> listarTodos();
}

3. Infraestrutura SQLite: br.com.bookstore.dao.LivroDAOSqlite

  • Inicialização Determinística: No construtor da classe DAO, execute um CREATE TABLE IF NOT EXISTS livros (id INTEGER PRIMARY KEY AUTOINCREMENT, titulo TEXT NOT NULL, autor TEXT NOT NULL, preco REAL NOT NULL);.
  • Gerenciamento de Recursos: Todo método deve usar try-with-resources para fechar Connection, PreparedStatement e ResultSet sem vazamentos.
  • Captura do ID Autoincrement: No salvar, utilize Statement.RETURN_GENERATED_KEYS e atribua o ID com livro.setId(...).
  • Mapeamento Centralizado: Isole a extração das colunas em private Livro mapearLinha(ResultSet rs) para evitar duplicação de código.

4. Roteiro Canônico de Testes no Main.java

  1. Instancie LivroDAO dao = new LivroDAOSqlite(); (aplicando DIP / Inversão de Dependência).
  2. Persista 3 obras literárias (ex: "Clean Code", "Design Patterns", "Refactoring") com autores e preços distintos. Verifique no console se os IDs 1, 2 e 3 foram gerados.
  3. Consulte o livro de ID 2. Utilize o método funcional buscarPorId(2L).ifPresentOrElse(...) para imprimir os dados completos ou emitir aviso amigável.
  4. Consulte um ID inexistente (ex: 999L) e demonstre que a aplicação não estoura NullPointerException.
  5. Chame listarTodos() e imprima os registros formatados com cabeçalho tabular.
